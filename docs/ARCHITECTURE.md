# Architecture

## Runtime

The production runtime is the Timeweb VPS:

- PostgreSQL 16, n8n, the existing collectors and EFA Read MCP running in Docker
- AI Analyst generated by the existing host cron at 16:00 Europe/Moscow
- one compact Analyst delivery at 16:30 through the active n8n Email and Telegram workflow
- Control Center running as one local-only systemd service behind Caddy and Basic Auth
- OZON Seller API as the external source
- OpenAI model used by the AI analyst

GitHub is the source-control and documentation layer, not the production runtime.

## Data flow

OZON API -> existing collectors/n8n -> PostgreSQL raw/operational tables ->
`mcp_read` -> AI Analyst -> Price Decision / Compact Report / Control Center.

Daily demand remains in `mcp_read.product_daily_performance`. Period financial
economics use the read-only
`mcp_read.product_period_economics(from_date, to_date)` function and are not
reconstructed by summing daily economics.

## Current analytical layers

EFA Read MCP exposes nine read-only tools over curated `mcp_read` sources.
Product demand, prices, stocks, promotions, CPC and regional logistics remain
separate from the period-aware financial function. AI Analyst consumes these
read sources and produces recommendations without changing Ozon state.

Regional logistics is built from posting logistics joined to postings and
finance operations. The analysis uses destination cluster, order count,
average logistics, baseline logistics, logistics delta, logistics delta
percentage, logistics rate, baseline logistics rate, and rate delta in
percentage points.

Confidence is based on regional order count:

- LOW: <= 2 orders
- MEDIUM: 3–4 orders
- HIGH: 5–9 orders
- VERY_HIGH: >= 10 orders

The summary layer classifies confirmed problems, weak signals, and low-confidence signals separately.

## Workflow boundaries

The canonical n8n workflow should remain the orchestration layer. Business calculations that need persistence or SQL aggregation belong in PostgreSQL views/queries rather than being duplicated across JavaScript nodes.

Credentials must remain in local n8n credential storage. They must not be committed to GitHub.

## CPC asynchronous reports

CPC Performance reports use a durable two-stage lifecycle. The 07:30 create
workflow reserves one `business_date`, creates at most one report and stores
its UUID; a separate bounded poller checks leased pending UUIDs and performs
download/persistence only when the report is ready. `cpc_collection_runs` is
the lifecycle source of truth. See
[`CPC_ASYNC_REPORT_LIFECYCLE_V1.md`](architecture/CPC_ASYNC_REPORT_LIFECYCLE_V1.md).

## Repository principle

One canonical production workflow JSON. SQL and documentation are versioned separately. Changes are made incrementally and recorded in Git history.
